# U6: the gateware carries only what is built in

Milestone M2, status 📅. Open (one line, as in the TODO table): Not started; costs one Vivado run, so it rides with the next gateware change

Alex, 2026-11-01, after reading how the SID chain fits together: *"Unsere Engine => Raus, wir heben hier nur
auf, was auch verbaut ist"*, and on the cost: *"ne, ich will keinen Vivado lauf. Aber ein Uxx todo, dass wir

## 1. What this is about

The tree under `cores/` and `designs/` carries sources that the shipped bitstream does not contain. They
cost nothing in LUTs — Vivado drops what is not instantiated — but they are read into every build, they sit
in `gateware_key` (`ci/lib.sh` hashes `designs constraints cores …`), and they make the tree say that
something is part of the firmware when it is not. A reader cannot tell the difference.

## 2. Known

- **`cores/trx_sid/rtl/trx_sid_engine.v`** (1024 lines), our own SID engine (T25.1). Verified against
  `cores/trx_sid/model/sidref.cpp` cycle by cycle, but not built since 2026-10-07: the shipped bitstream
  takes the voices from reDIP (`SID_MULTI`, `cores/icepi/c64_redip_sid/sid_multi.sv`). What goes with it:
  - its tables in `cores/trx_sid/mem/`: `sid_wf_data.mem`, `sid_wf_dir.mem`, `sid_curve_init.mem`.
    **`decim_fir.mem`, `decim_hb1.mem`, `decim_hb2.mem` stay** — they belong to the mixer `trx_audio.v`.
  - the part of `cores/trx_sid/model/` that only serves the engine. **`design_decim.py` stays**: the mixer's
    coefficients come from it (header of `trx_audio.v`).
  - the benches under `designs/c64_basic/sim/sid/` that compare the engine against the model
    (`designs/c64_basic/sim/sid/build.sh` names it). They are not in CI: the header of `ci/sims.txt` lists
    `sid` under "not listed, and why" because it fetches libresidfp and only reports. So nothing in the
    pipeline depends on them.
  - two lines in `ci/sims.deps`: `@vcore` (line 30) takes `cores/trx_sid` as a whole, so every bench built
    on it gets a new key when a file there goes - cheap, but it re-runs them once. And `redip_new`
    (line 90) declares `cores/trx_sid/mem/sid_curve_init.mem`, which only `trx_sid_engine.v` ever read
    (`$readmemh`, line 258): with the engine gone that dependency was already stale - reDIP lost its
    loadable curve table in T25.5.
  - the `TRX_SID=1` branch in `designs/c64_basic/build.tcl` and the `` `ifdef SID_MULTI `` / `` `else ``
    switch in `cores/trx_sid/rtl/trx_sid.v`.
- **The 2-SID reDIP path** (`TRX_SID=redip2`, `` `ifdef SID_REDIP `` in `c64_top.v`): the build before
  2026-10-07, not shipped since.
- **`sid=` in `KEY_EXTRA`** (`gateware_key`, `ci/lib.sh`) and `T16_SLOT`: a key field for a variant nobody
  builds is dead weight once the variant is gone.
- **Everything else `trx_tree` pulls in.** `designs/c64_basic/build.tcl:73` reads the whole of
  `cores/icepi` into the project. What of it is never instantiated is not inventoried; doing that is part
  of this task, not a guess to make here.

## 3. What it costs, and when it happens

Every file under `cores/` or `designs/` is in `gateware_key`, so removing one is a cache miss and a Vivado
run (measured: 9.2 min on the builder, 32.7 min on the NAS). The design does not change — the removed
sources are not instantiated — but the `.bit` is a new file with a new sha256, so the firmware that is
published stops matching a build of the tree.

Therefore: **this never runs on its own.** It rides with the next change that rebuilds the bitstream anyway,
and the release that carries it says that the bitstream changed without the hardware changing.

## 4. Done when

- A build of `c64_basic` reads only files that end up in the design, or the exceptions are named in the
  build script with their reason.
- Utilization and worst slack of the build before and after are compared and the difference stated; the
  benches of `ci/sims.txt` are green.
- `TRX_SID` is gone or documents a variant that exists.
- `PROVENANCE.md` and `cores/icepi/ORIGIN.md` no longer list anything the firmware does not contain.
