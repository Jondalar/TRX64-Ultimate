1Introduction and goals

The machine today starts straight into BASIC. The firmware's own interface (Gideon's file browser, or Commodore's menu on a C64U) appears only when the menu button is pressed. The TREX Launcher is a screen of our own that the firmware shows between power-on and the running machine, and that the menu button can reach again later.

Goals

#GoalWhy
G1A start screen that belongs to TREX: titles, cartridge slots, dump and write, snapshots, one step from power-on.The TREX tools are spread over context menus of a browser that is not ours.
G2Separation from Gideon's code: TREX lives in its own module and joins the firmware at as few places as possible.Every upstream release is merged by hand; each touched upstream file is a conflict waiting.
G3A look of its own (charset, colours, logo) without restyling the upstream UI.Idea 1 ("a TREX UI with more style") comes along for the screen that is ours.
G4Never in the way: a boot that goes straight to BASIC stays one setting away.The machine is a C64 first.

The selector, as the user sees it

Something like GRUB, in front of the interfaces:

  • Holding the C= key at power-on opens the selector: TREX, Ultimate, Commodore.
  • The last choice is remembered and booted without asking next time.
  • A setting makes the selector appear at every power-on.
  • From the freeze menu and the overlay menu the user can go back to the selector.
  • The interfaces run as separated from each other as possible.
No C64 program is needed for this. Which interface appears, and when, is decided in ultimate_main() by the firmware; the screen is drawn by the firmware on a host it owns (the frozen C64 or the video overlay), like the existing menus.

In scope: what the firmware shows at boot and at the menu button, the module that draws it, the seam into ultimate_main(). Out of scope: changes to the FPGA, to the C64 ROMs, and a restyle of the upstream browser.

4Solution strategy

  1. A third front door. ultimate_main() already chooses the root object of each UserInterface: TreeBrowser for the Ultimate interface, CommodoreMenu for the Commodore one (ultimate.cc:147-183). The launcher is one more UIObject in that same place. Its entries open the existing browser, settings and TREX tools as objects pushed on top of it.
  2. Shown once at boot. After c64->start() (ultimate.cc:112) the firmware runs the launcher once, the way the menu button runs the UI (run_once()). Leaving it lets the machine run on.
  3. Its own directory. software/trex/launcher/ holds the object, its theme and its settings. Upstream files get one include and one call each.
  4. Style through the theme table. t_ui_theme (ui_mode.h) is already the place where the two interfaces differ; a TREX row adds what the launcher draws with.

4.1 Variant K: kickstart modules

Proven on RISC-V by the Spiffy / prkl firmware ("Kickstart", commit 9bf40b1): kickstart.ue2 is started like an update, embeds a whole ultimate.app, checks the FPGA and ESP32 versions and a checksum, copies the application to 0x00030000 and jumps to it. The flash is not touched; a power cycle returns to the installed firmware.

Why the RISC-V way needs one more rule here

  • Loading ultimate.app through "Run Update" does not work: the record is read straight to its load address 0x0 with no range check (filetype_u2p.cc:165-176) and overwrites the running firmware.
  • The Nios has no movable trap vector. The vector at 0x0 is inside the destination, so the copy must run with interrupts off and must not be able to trap (no calls, no software mul/div).
  • Taking over 0x0 from a program at 0x03000000 is what the Nios updater already does (alt_load.c:66-85); the firmware's crt0.S already starts from a warm machine (status off, stack, BSS, itu_clear_irqs).

Entry contract

The image bytes at 0x0 as the boot ROM would put them; jump to the record's start (0x234); interrupts off (status.PIE=0, no ITU interrupt enabled or pending); no bus master writing into 0x0–0xEA0000. The new firmware needs no change.

Quiesce before the copy: wrctl status,0, itu_clear_irqs(), WiFi UART IRQ off (alt_load.c:66-70), USB DMA off (NANO_START=0, usb_base.cc:377), network receive off (RMII_RX_ENABLE=0, rmii_interface.cc:113), esp32.Quit(). Other bus masters (sampler, data streams, command interface) not yet audited. After the copy: read back and compare, then an initi/flushd sweep over the image in case the real core has caches the BSP does not show.

Checks before the jump

  1. Board: CAPAB_ULTIMATE64 and FPGA type 0 or 1 (update_u64.cc:105).
  2. Core version: C64_CORE_VERSION and ITU_FPGA_VERSION equal to the values of the RBF the image was built for. Kickstart never loads an RBF, so this is the check that matters; where the expected value comes from at build time is open.
  3. Image: checksum (update_common.h:34-46), load 0, start inside the image, image plus BSS below 0xEA0000.
  4. ESP32 bridge version: warn only.

On a failure after the point of no return (A): show why, then power off (update_common.h:53-62); the next power-on boots the flash firmware.

What must be tried first on a MK1

  1. Kickstart the identical installed build: shows whether the firmware takes a warm start.
  2. Kickstart twice and compare a RAM checksum after boot: shows whether any DMA still writes into low RAM.
  3. A changed build that prints its build ID: shows the copy and the cache sweep work.

A JTAG load with openFPGALoader -m configures the FPGA only; the boot ROM then loads the firmware from flash. It is not a firmware run from RAM and does not answer point 1.

7Deployment view

  • The launcher is compiled into the firmware image (.ue2/.cfw for U64-II/C64U, .u64 for U64). No separate flash area.
  • Its settings live in a config store like every other page, in the flash the firmware already writes settings to.
  • Assets (a TREX charset, a logo) are either tables in the image or files on /Flash; the image stays self-sufficient if the file is missing.
  • TREX apps (trex_crt.u2a) stay separate and are started from the launcher through the App Loader.

11Risks and technical debt

  • Freeze right after start(). C64::freeze() returns without freezing when phi2_present() is false (c64.cc:1257). Whether the clock is there immediately after start() is not verified.
  • A cartridge that starts itself. An EasyFlash or EF3 boots its own menu at reset. A launcher at boot must either come first (and start the cartridge afterwards) or not appear when a cartridge is active.
  • Overlay without HDMI. The main loop only takes the overlay when HDMI hot-plug is seen (ultimate.cc:206). Host B must fall back.
  • Keyboard matrix. The USB keyboard is switched off the C64 matrix while a UI runs (ultimate.cc:221-223); a boot-time run has to do the same.
  • C= at power-on. The keyboard matrix is read by the FPGA (U64II_KEYB_ROW/COL, ultimate.cc:134); whether it is readable that early in the boot is not verified.
  • Kickstart on the U64 MK1. Only proven on RISC-V. The Nios design (4.2) rests on code the updater already runs; a warm start of the firmware, remaining DMA into low RAM and the core version check are untried on hardware.
  • Module and FPGA versions (variant K). A TREX firmware module is tied to the FPGA core and ESP32 version of the base it is started from.
  • Commodore firmware on the C64U. Commodore's own releases may add start-up behaviour; the launcher must stay in front of our build only.
